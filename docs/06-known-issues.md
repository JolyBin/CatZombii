## 1 — Четвёртый питомец роняет бой

**Статус: ✅ починен в `d162c4db`.** Взят третий вариант правки из списка ниже:
лимит состава больше не константа. `AddFriend` и `AddEnemy` сравнивают с
`UIBattleWindow.FriendlyPositionsCount` / `EnemyPositionsCount`, то есть с длиной
массивов позиций в сцене — код и сцена перестали расходиться в принципе.
`First` заменён на `FirstOrDefault`, обращения к позиции идут через `?.`:
при рассинхроне юнит останется без слота, а не уронит `InvalidOperationException`.

**Где:** [`BattleController.cs:120-141`](../Assets/Scripts/Runtime/Battle/BattleController.cs#L120)
+ `UIBattleWindow._friendlyPositions` в сцене

**Суть:** код разрешает до 4 живых союзников, а в сцене под них только **3** слота.

```csharp
public void AddFriend(UnitConfig unit)
{
    if (_friendlyList.Count == 4)     // ← вытеснение только при 4
        _friendlyList[0].Health.Die();
    ...
    UIUnitPosition unitPosition = _battleWindow.SetFriendPosition();
    // SetFriendPosition() = _friendlyPositions.First(x => x.IsFree)
    // при 3 занятых слотах → InvalidOperationException
}
```

**Воспроизведение:** играть за Necromancer'а, призвать четвёртого питомца до того,
как умрёт первый. Например: `Dark > Venom` ×2, затем `Dark > Venom > Dark > Venom`
(призывает сразу двоих).

У врагов такой проблемы нет — там 4 слота и лимит 4 совпадают.

**Варианты правки:**
- заменить `== 4` на `== 3` в `AddFriend` (быстро, но константа снова зашита);
- добавить 4-й слот в сцену (сохраняет задуманный лимит);
- лучше: брать лимит из `_friendlyPositions.Length`, чтобы код и сцена не расходились.

## 2 — Генератор элементов исчерпаем

**Статус: ✅ починен в `d162c4db`.** Пул перезаполняется при опустошении
(`ElementsGenerator.RefillIndexes`), то есть стал бесконечным. Bag-семантика —
выдача без возврата, а значит ровное распределение внутри цикла — сохранена.

**Где:** [`ElementsGenerator.cs:43-53`](../Assets/Scripts/Runtime/Flask/ElementsGenerator.cs#L43)

```csharp
int rndIndex = Random.Range(0, _elemntIndexes.Count);
int elementIndex = _elemntIndexes[rndIndex];
...
_elemntIndexes.RemoveAt(rndIndex);   // ← никогда не возвращается обратно
```

Пул — 500 индексов, создаётся в `FlaskController.Init()`. Каждое схлопывание колбы
забирает 4. Примерно **125 схлопываний за бой**, дальше `Random.Range(0, 0)`
возвращает 0, обращение к пустому списку → `ArgumentOutOfRangeException`.

Пул пересоздаётся на каждый бой, так что мгновенной смерти нет. Но затяжной уровень
(особенно босс с 450 HP) до лимита дожить может.

**Правка:** либо возвращать индекс в пул после выдачи, либо не удалять вовсе
(`RemoveAt` тут вообще не нужен для равномерности), либо перезаполнять пул при опустошении.

## 3 — `UnitRuntime.Dispose()` — мина

**Статус: ✅ починен в `d162c4db`** ровно предложенной правкой: `_unitSpell?.DisposeSpell();`.
Пассивных юнитов (`AttackCooldown = 0`) теперь можно делать.

**Где:** [`UnitRuntime.cs:44-51`](../Assets/Scripts/Runtime/Battle/UnitRuntime.cs#L44)

```csharp
public UnitRuntime(UnitConfig unit, BattleController battleController)
{
    ...
    if (unit.AttackCooldown > 0)
        _unitSpell = unit.AttackConfig.GetUnitSpell();   // ← только здесь
}

public void Dispose()
{
    ...
    _unitSpell.DisposeSpell();    // ← безусловно
}
```

Юнит с `AttackCooldown = 0` не получает `_unitSpell`, но `Dispose()` всё равно
его дёргает → `NullReferenceException` при смерти.

**Сейчас не стреляет:** у всех шести юнитов в проекте кулдаун ненулевой (1500–5000).
Но первый же пассивный юнит — щит, тотем, декоративный союзник — уронит игру.

**Правка:** `_unitSpell?.DisposeSpell();`

## 4 — Переполнение стола

**Статус: ✅ починен в `d162c4db`.** У окна появился `IsFull`, и проверка стоит
с обеих сторон: `UITableWindow.ShowFullFlask` выходит рано, а `TableController`
не кладёт элемент в `_currentElements` — модель и вид остаются согласованы.
Выбран самый дешёвый из трёх вариантов: элементы сверх шестого **молча теряются**.
Автопроверка при заполнении стола осталась в силе как дизайнерская задача —
в [10 — Дизайн игры](10-progression-design.md) переполнение превращается в механику
(котёл закипает и варится сам).

**Где:** [`UITableWindow.cs:50-56`](../Assets/Scripts/Runtime/Spells/UI/UITableWindow.cs#L50)

```csharp
public void ShowFullFlask(Sprite sprte)
{
    UIFullFlask newFlask = _flasks[_curretnEmptyPositions];   // ← без проверки границ
    _curretnEmptyPositions++;
```

На столе 6 слотов. Собрал 7 элементов, не нажав «проверить» → `IndexOutOfRangeException`.

Самая длинная комбинация в игре — 4 элемента, так что копить 7 незачем.
Но игрок этого не знает, и ничто его не останавливает.

**Правка:** либо игнорировать элементы сверх лимита, либо (лучше) автоматически
проверять комбинацию при заполнении стола, либо блокировать схлопывание колб
при полном столе.

## 5 — Успех и провал комбинации выглядят одинаково

**Статус: ✅ починен в `f6e26ecd`** (И1) — ровно как и планировалось: фидбек пошёл
вместе с котлом, а не в подачу. `ShowResult` использует `result` и разводит успех
и провал **двумя каналами сразу**: цветом (`_successColor` / `_failColor`) и
кинематикой — успех подпрыгивает (`DOPunchScale`), провал трясётся вбок
(`DOShakeAnchorPos`). Сигнал «только цветом» запрещён
([12 §4.4](12-game-field-and-ui.md)), поэтому одного цвета было бы мало.

Историческое обоснование приоритета (01.08.2026): с часами котла
([10 §1](10-progression-design.md)) провал перестаёт быть бесплатным — он стоит
игроку накопленной цепочки **и** тактов, которые утекли на кольце. Невидимый провал
в такой конструкции ломает главную обратную связь ядра, поэтому фидбек шёл в И1
вместе с котлом, а не откладывался в подачу
([12 §8, строка 3](12-game-field-and-ui.md), шаг М4).

**Где:** [`UITableWindow.cs:67-70`](../Assets/Scripts/Runtime/Spells/UI/UITableWindow.cs#L67)

```csharp
public void ShowResult(bool result, string name)
{
    _resultMergeText.text = name;   // ← result не используется вообще
}
```

При провале `TableController` передаёт строку «Ничего не получилось((»,
при успехе — название заклинания. Оба текста рисуются одинаково: нет цвета,
нет звука, нет анимации различия.

Это **не крэш, а дизайнерская дыра**: игрок не понимает, попал он или слил элементы.

**Правка:** использовать `result` — цвет текста, разная анимация, звук.

> **Дополнение 01.08.2026: провалиться можно двумя разными способами, и оба реальны.**
> Ветка провала не исчезнет от закона префикса ([10 §6](10-progression-design.md)) —
> он говорит про префиксы **рецептов**, а не про цепочку, которую по факту набрал игрок.
> На сегодняшнем контенте Warrior'а:
>
> 1. **Чужое схлопывание.** Игрок не выбирает, что схлопнется, — только когда нажать
>    проверку. Собирал `Fire`, схлопнулась колба `Fighting` → в котле `Fire > Fighting`.
>    Такой цепочки нет ни среди пяти рецептов, ни среди их префиксов.
>    `Table.TryGetSpell` не находит узел и выходит по `Table.cs:65`.
> 2. **Остановка на внутреннем узле.** `Fighting > Fighting` в дереве существует —
>    по дороге к ультимейту `Fighting > Fighting > Fire`, — но заклинания на этом узле
>    нет. Узел найден, `spell` пуст, выход по `Table.cs:70` (`return spell != null`).
>
> Первый способ — сама природа пазла, второй — прямое следствие того, что закон префикса
> текущим контентом ещё не выполнен (`Fighting > Fighting` обязан стать рецептом —
> задача к контенту). Сообщение о провале живёт в `TableController.cs:50`, а не
> в `UITableWindow` — удалять его нельзя.

## 6 — `RepitsCommand.Invoke` без null-проверки

**Статус: ✅ починен в `d162c4db`** предложенной правкой. Заодно ушла и вторая
половина хрупкости: после `fa1b425a` вид колбы перерисовывается по событию модели,
поэтому от порядка вызовов внутри `FlaskController` он больше не зависит.

**Где:** [`Flask.cs:59`](../Assets/Scripts/Runtime/Flask/Flask.cs#L59)

```csharp
_stack.Clear();
RepitsCommand.Invoke(firstElement);   // ← должно быть RepitsCommand?.Invoke
```

Сейчас спасает только порядок инициализации: `FlaskController.Init()` наполняет
колбы через конструктор и `UpdateFlask()` (которые не вызывают `CheckRepits`),
а подписка происходит позже в `SubscribeToMove()`.

Поменяется порядок — получишь `NullReferenceException`. Хрупко на ровном месте.

**Правка:** `RepitsCommand?.Invoke(firstElement);`

## 7 — Стан вместо паузы жжёт CPU

**Статус: ✅ починен в `d162c4db`, окончательно закрыт в `2e6d1bb4`.** Сначала шаг
таймера стал константой `TIMER_STEP = 100`, пауза — отдельным флагом `_isPaused`,
а `UniTask.Delay` — всегда 100 мс; цикл получил токен боя и завершался по отмене,
а не крутился до `Dispose`.

С переходом в пошаговый режим баг стал **невоспроизводим по построению**: в
`TargetController` больше нет ни цикла, ни `Delay` — только `Tick()`, который
приходит из `WorldClock` на действие игрока. Стан считается в тактах
(`Stun(int tacts)`, поле `_stunTacts`) и просто съедает ход, а не «тает» по
настенным часам. Жечь CPU нечему: между действиями игрока не выполняется ничего.

**Где:** [`TargetController.cs:31-39, 99-112`](../Assets/Scripts/Runtime/Battle/TargetController.cs#L31)

```csharp
public void StopAttack()  => _timerStep = 0;
...
while (_isLive)
{
    CurrentTimer = Math.Clamp(CurrentTimer - _timerStep, 0, _startTimer);
    ...
    await UniTask.Delay(_timerStep);   // ← Delay(0) на время стана
}
```

`_timerStep = 0` означает и «таймер не идёт» (логически верно), и `UniTask.Delay(0)` —
то есть цикл начинает крутиться на каждом кадре вместо раза в 100 мс.

Стан работает, но на время стана юнит жжёт CPU. На слабом железе в WebGL при
нескольких застаненных юнитах это заметно.

**Правка:** развести «шаг таймера» и «пауза» — отдельный флаг `_isPaused`,
а `Delay` всегда с константой 100 мс.

## 8 — `SelectEnemyTarget` не проверяет текущую цель

**Статус: ✅ починен в `d162c4db`.** `SelectEnemyTarget` проверяет `HeroTarget`
на null, `SelectedLastTarget` зануляет его при пустом списке, `Exit()` — тоже.
Дополнительно `PowerAttack` и `FastAttack` перестали доверять непустому
`EnemySquad` и сами проверяют `HeroTarget`.

**Где:** [`BattleController.cs:152-165`](../Assets/Scripts/Runtime/Battle/BattleController.cs#L152)

```csharp
private void SelectEnemyTarget(UnitRuntime unitRuntime)
{
    HeroTarget.UIUnit.Selected(false);   // ← HeroTarget может быть null
    ...
}

private void SelectedLastTarget()
{
    if (_enemyList.Count == 0)
        return;                          // ← выходит, оставляя старую ссылку
    ...

```

`SelectedLastTarget` при пустом списке врагов оставляет `HeroTarget` протухшим.
Последующий клик по врагу новой волны обратится к уничтоженному объекту.

**Правка:** занулять `HeroTarget` при пустом списке и проверять на null в `SelectEnemyTarget`.

Все 8 заклинаний этих двух героев висят на этом классе-заглушке. Выбрал героя,

## 10 — События зануляются во время собственного вызова

**Статус: ❌ открыт.** `Health.Die()` не менялся: `OnDied?.Invoke()` и следом
`Dispose()`, который зануляет все события.

**Где:** [`Health.cs:76-80`](../Assets/Scripts/Runtime/Battle/Health.cs#L76)

```csharp
public void Die()
{
    OnDied?.Invoke();
    Dispose();        // ← зануляет OnDied, OnChanged и остальные
}
```

Работает, потому что `Invoke` уже скопировал список подписчиков. Но подписчик,
добавленный *внутри* обработчика `OnDied`, молча потеряется.

Не проявляется в текущем коде, но это ловушка при добавлении реакций на смерть.

## 11 — Питомцы не останавливаются при смерти героя → победа поверх поражения

**Статус: ✅ починен в `d162c4db`.** Лямбда на `HeroHealth.OnDied` заменена методом
`HeroDie` → `EndBattle()`, который останавливает **обе** стороны и отменяет токен боя.
Флаг `_isBattleOver` не даёт волне «закончиться» после конца боя, поэтому
`OnAllEnemyDie` больше не сработает поверх поражения. Подписки снимаются
в `BattleController.Exit()` и `StepsController.Exit()` — предложенная правка
выполнена целиком.

**Где:** [`BattleController.cs:56-63`](../Assets/Scripts/Runtime/Battle/BattleController.cs#L56)

```csharp
HeroHealth.OnDied += () =>
{
    OnHeroDie?.Invoke();
    foreach (var item in _enemyList)      // ← только враги
    {
        item.TargetController.StopAttack();
    }
};
```

`StopAttack()` рассылается только по `_enemyList`. Питомцы Necromancer'а из `_friendlyList`
продолжают бить. Если они добьют последнюю волну уже после смерти героя, сработает
`OnAllEnemyDie` (строки 105–111) и **окно победы откроется поверх окна поражения**.

**Воспроизведение:** играть за Necromancer'а, призвать питомцев, умереть на последней
волне при живых врагах с малым HP.

**Правка:** останавливать обе стороны, плюс снимать подписку на `OnAllEnemyDie` после
смерти героя.

## 12 — Пазл остаётся интерактивным под окном поражения

**Статус: ✅ починен полностью — половина в `d162c4db`, вторая в `2e6d1bb4`.**

Первая половина: бой останавливается. `EndBattle()` гасит таймеры обеих
сторон и отменяет токен боя, поэтому циклы `TimerAttack` завершались, а не крутились
до нажатия «Продолжить». Умножение [бага №7](#7--стан-вместо-паузы-жжёт-cpu) на число
врагов исчезло вместе с самим багом №7.

Вторая половина закрыта пошаговостью. Появился `StepsController.FinishParty()`,
который зовётся из **обоих** окон итога — `ShowWinWindow` и `ShowLoseWindow` — и
делает три вещи: `WorldClock.Stop()` (мир больше не принимает действия),
`FlaskController.LockInput()` (колбы не принимают ни выбор, ни перелив; уже поднятая
колба опускается) и `TableController.LockInput()` (`CheckRepit` выходит рано, то есть
заклинание не может прилететь в уже закончившийся бой). Пошаговость сделала лечение
полным: **остановить приём действий = остановить мир**, отдельного «замораживателя»
не требуется. По той же причине отпала и пауза боя для рекламы и сворачивания
браузера, которая раньше числилась в скоупе фазы 1
([09](09-platform-strategy.md), [10 §8](10-progression-design.md)).

Правка живёт в [`StepsController.cs`](../Assets/Scripts/Runtime/Steps/StepsController.cs),
методы `FinishParty` / `ShowWinWindow` / `ShowLoseWindow`.

**Где:** [`StepsController.cs:68-76`](../Assets/Scripts/Runtime/Steps/StepsController.cs#L68)

`ShowLoseWindow` просто показывает окно. `FlaskController` и `TableController` остаются
подписанными и живыми — игрок может продолжать переливать шарики и варить заклинания,
пока висит «ты проиграл». То же и с окном победы.

Кроме того, `_isLive` у врагов остаётся `true`, а `StopAttack()` выставляет
`_timerStep = 0` → `UniTask.Delay(0)` крутится каждый кадр **для каждого врага** вплоть
до нажатия «Продолжить». То есть [баг №7](#7--стан-вместо-паузы-жжёт-cpu) в момент
поражения умножается на число врагов.

Оба симптома — следствие того, что **паузы боя в игре не существует**. Она всё равно
нужна для рекламы и для сворачивания мобильного браузера
(см. [09](09-platform-strategy.md), скоуп фазы 1).

## 13 — Отмены не существует нигде: заклинания живут дольше боя

**Статус: ✅ починен в `d162c4db`** ровно предложенной правкой. `StepsController`
держит токен партии и отменяет его в `Exit()`; `BattleController` создаёт связанный
токен боя (`BattleToken`) и отменяет его при смерти героя, победе и выходе.
Сигнатура стала `UniTask ApplySpell(BattleController, CancellationToken)` — обновлены
все 7 реализаций, `async void` не осталось ни одного. Единственная точка запуска
ловит `OperationCanceledException` тихо, всё прочее пишет `Debug.LogException`,
так что в WebGL исключения больше не глотаются молча. Регенерация не лечит после
выхода из боя, стан не зовёт `ContinueAttack` на уничтоженной цели, босс не спавнит
зомби в мёртвый бой. Рецепт для новых заклинаний — в [05 — Как расширять](05-extending.md).

**Где:** [`BaseSpellConfig.cs`](../Assets/Scripts/Runtime/Spells/Models/BaseSpellConfig.cs),
все `ApplySpell`

`ApplySpell` объявлен `async void`, а `CancellationToken` не встречается в проекте **ни разу**.
Последствия уже есть в текущем контенте:

- `Regeniration.ApplySpell` крутит цикл с `UniTask.Delay(2000)` и продолжает лечить
  `HeroHealth` **после** `StepsController.Exit()`;
- `FastAttackSpell` ждёт `_stunTimer * 1000` мс и потом зовёт `ContinueAttack()` —
  цель к этому моменту может быть мертва и `Dispose()`-нута.

При Exception Support = «Explicitly Thrown Only» в WebGL это глотается молча: игрок видит
странное поведение, разработчик не видит ничего. Каждый новый таймер (часы котла, пакости)
умножает число осиротевших циклов.

**Правка:** `CancellationTokenSource` на партию, `ApplySpell(BattleController, CancellationToken)`.

## 15 — У колбы два источника истины о содержимом

**Статус: ✅ починен в `d162c4db` + `fa1b425a`.** Единственный источник истины —
модель `Flask`: она отдаёт содержимое наружу и поднимает событие после любой мутации,
вид подписан на это событие и рисуется из состояния. Собственного счётчика
у виджета нет, порядок вызовов больше ни на что не влияет.

Сопутствующее ограничение модели снято **частично**: узнать, сколько в колбе
элементов и каких именно, теперь можно снаружи (`Count`, `MaxSize`, содержимое
от дна к горлышку) — механика «в самую полную колбу» пишется. А вот индекса
и порядка у колбы по-прежнему нет: они лежат в `Dictionary<Flask, UIFlask>`,
так что «третья слева» всё ещё требует рефактора хранения.

> Область колб сейчас в активной работе — конкретные имена методов вида
> здесь намеренно не фиксируются.

**Где:** [`UIFlask.cs`](../Assets/Scripts/Runtime/Flask/UI/UIFlask.cs) (`_currentIndex`)
против [`Flask.cs`](../Assets/Scripts/Runtime/Flask/Flask.cs) (`_stack`)

`UIFlask` ведёт собственный счётчик `_currentIndex` параллельно `Flask._stack`. Сегодня они
синхронны только потому, что колбу двигает **единственный** путь — клик игрока. Любой новый
путь мутации (часы котла, пакость, повадка кота, автопереливание) рассинхронит их молча.

Сопутствующее ограничение модели: колбы лежат в `Dictionary<Flask, UIFlask>`, то есть
**у колбы нет ни индекса, ни порядка**, а наружу `Flask` отдаёт только
`IsPossiblePushElement` / `IsPossiblePopElement` — узнать, сколько в ней одинаковых,
невозможно. Любая механика, целящаяся «в самую полную колбу», требует рефактора модели.

**Правка:** единый путь мутации, `UIFlask` перестаёт вести свой счётчик и становится
чистым отображением.

## 16 — `AddEnemy` вытесняет второго врага, а не первого

**Статус: ❌ открыт.** Найдено при сверке `d162c4db`: правка лимитов сохранила
исходную странность, а не внесла её.

**Где:** [`BattleController.cs`](../Assets/Scripts/Runtime/Battle/BattleController.cs),
`AddEnemy`

```csharp
if (_enemyList.Count >= _battleWindow.EnemyPositionsCount)
{
    _enemyList[Math.Min(1, _enemyList.Count - 1)].Health.Die();
}
```

Жертву выбирает индекс `1` — это не самый старый враг (`[0]`) и не самый слабый,
а просто **второй по порядку спавна**. Правило целиком держится на порядке
добавления в список, нигде не объяснено и игроку невидимо: враг умирает сам собой
и засчитывается как убитый со всеми последствиями (`Health.Die` → снятие
с позиции → проверка конца волны).

Реально это достижимо на боссе: в третьей фазе он раз в 15 с добавляет трёх зомби
при четырёх позициях в сцене, то есть вытеснение идёт каждый спавн.
Ср. `AddFriend`, который в такой же ситуации убивает `[0]` — две стороны ведут себя
по-разному без причины.

`Math.Min` спасает от выхода за границы, но не от логики: если позиций для врагов
в сцене окажется одна, вытеснение обнулит `_enemyList` и **досрочно закроет волну**.
Сегодня позиций 4, поэтому не стреляет.

**Правка:** решить правило осознанно — «вытесняем самого старого» (`[0]`),
«самого слабого по HP» или «не спавним вовсе, пока нет места» — и не убивать
последнего оставшегося врага.

## 17 — Регенерация лечит по настенным часам: простой лечит бесплатно

**Статус: ✅ починен в `2e6d1bb4`** — в том же коммите, который её и создал: это дыра,
которую **породила смена модели времени**, а не старый код.

**Где:** [`RegenirationConfig.cs`](../Assets/Scripts/Runtime/Spells/Models/Warrior/RegenirationConfig.cs)

Пока игра была реальновременной, `Regeniration` крутила `UniTask.Delay(_timer)` между
тиками лечения, и это было корректно: пока лечение капало, враги били. Пошаговость
разорвала связку — враги ходят только когда ходит игрок, а `Delay` продолжал идти
по настенным часам. Итог: **игрок, который просто перестал переливать, лечился даром
и в полной безопасности**. Единственное лечение в игре сводилось к «сварил и подожди»,
без единого решения — ровно та лазейка, ради закрытия которой все остальные таймеры
и переводились в такты.

Заметить это по чек-листу «перевести таймеры в такты» было нельзя: `Regeniration` —
не таймер юнита, у эффекта нет носителя, поэтому он не попадал ни в
`TargetController`, ни в `BattleController.TickSquad` и остался бы **единственным
куском real-time в пошаговой игре**.

**Как починено.** В `BattleController` заведено событие `OnTact` — точка подключения
для длящихся эффектов игрока без юнита-носителя; оно поднимается первой фазой боевого
такта. `Regeniration` стала синхронной (`ApplySpell` возвращает `UniTask.CompletedTask`),
подписывается на `OnTact` и сама считает `_tactsToNextHeal`. Интервал берётся в тактах
(`RegenirationConfig.IntervalTacts` через `WorldClock.TactsFromMilliseconds`), минимум
один такт — ноль означал бы тихое превращение регенерации в обычный хил. Первый тик —
немедленный, в том же такте, что и варка: игрок уже заплатил за неё ходом соседей,
и «варю лечение на трёх HP» иначе проигрывается по построению. `OnTact` зануляется
в `BattleController.Exit()` — длящийся эффект не переживает партию.

**Правило, которое из этого следует** (записано в
[04, «Что стоит знать»](04-architecture.md)): новая система, живущая во времени,
реализует `ITickable` и добавляется в `WorldClock`; эффект без носителя цепляется
к `OnTact`. `UniTask.Delay` для игровой длительности — всегда бесплатный ресурс
для того, кто перестал ходить.

## Предупреждения компилятора

После апгрейда на Unity 6.5 проект собирается **без ошибок**
(проверено в живом редакторе: `recompile_status → completed, errors: []`).

Остались предупреждения:

| Код | Где | Что |
|---|---|---|
| `CS0649` | ~25 полей в UI-классах | `[SerializeField]`-поля без присваивания в коде — норма для Unity |
| `CS0169` | `UIBattleWindow._currentFriendlyPositionIndex` | Неиспользуемое поле, можно удалить |
| `CS0618` | `Assets/PluginYourGames/Example/` | Устаревший API в демо-сценах вендора. Папку `Example` можно удалить целиком |

Предупреждения `CS1998` (`async` без `await` в конфигах заклинаний) больше нет:
после `d162c4db` заклинания без задержки возвращают `UniTask.CompletedTask`,
а `async` остался только там, где реально есть `await`.

`CS4014` (`TimerAttack()` не ожидается) ушёл вместе с самим методом в `2e6d1bb4`:
асинхронного цикла у `TargetController` больше нет, такт приходит извне.

Ни одно из оставшихся не блокирует сборку.
